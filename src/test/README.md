# Doer tests

## Kinds of tests

Each kind has its own system under test (SUT). The package of a test class tells its kind; the suffix of its name tells who runs it.

| Kind | System under test | Examples | Package |
|---|---|---|---|
| Unit | Doer classes in the test JVM, without the annotation processor | `DoerServiceTest` | `com.doer` |
| SQL | Doer's SQL on Postgres, generated by the processor | `DoerServiceJdbcITCase` | `com.doer` |
| Annotation processing | javac + `DoerProcessor`: javac messages, generated files, the output of the compiled code | `GeneratorITCase`, `GeneratorErrorsITCase` | `com.doer.processor` |
| Generated code, build tools | Transit Sims built by a build tool and run in its own JVM; `Main` wires the beans by hand | `JavacGeneratedCodeITCase`, `MavenGeneratedCodeITCase` | `com.doer.generatedcode` |
| Generated code, runtimes | the same checks on Transit Sims deployed in a runtime | `GeneratedCodeE2E` | `com.doer.generatedcode` |
| Runtime functional | Doer and the user's code in a runtime: CDI, transactions, REST, concurrency, restarts | `TransactionsE2E`, `ConcurrencyE2E` | `com.doer.e2e` |

The annotation processing tests check one feature or edge case per test, each on its own small sources. All the other kinds of the processor and the runtime run on **Transit Sims**, the test application in [`resources/e2e/transitsims`](resources/e2e/transitsims/README.md).

| Suffix | Runner | Where in CI |
|---|---|---|
| `*Test` | surefire, `mvn test` | job `java-compatibility`: JDK 17, 21, 25, 27 |
| `*ITCase` | failsafe, `mvn verify`, one JVM per class | job `java-compatibility`: JDK 17, 21, 25, 27 |
| `*E2E` | failsafe in the profile `e2e`, `mvn verify -Ddoer.e2e.runtime=<runtime>`, one JVM for all classes | job `runtime-e2e`: one runtime per job, JDK 25 |

## The same checks for build tools and runtimes

The checks of the generated code are `@Test` default methods of the interface [`GeneratedCodeTest`](java/com/doer/generatedcode/GeneratedCodeTest.java). Each implementation builds and starts Transit Sims its own way and implements `runTask(request)`:

```
GeneratedCodeTest                the checks: request → expected response of transitsims.validation.TaskRunner
├── JavacGeneratedCodeITCase     javac       → TransitSimsProcess: java transitsims.Main, JSON Lines over stdin/stdout
├── MavenGeneratedCodeITCase     mvn package → TransitSimsProcess
└── GeneratedCodeE2E             E2eEnvironment: deployed in Docker → POST /api/validation/run-task
```

A new build tool or a new runtime adds an implementation, not tests.

## Test helpers

No base classes for infrastructure. [`com.doer.testkit`](java/com/doer/testkit) has static helpers: `Toolchain` (`javac`, `java`, `mvn`, classpaths from the local Maven repository), `Sources` (sources from text blocks and test resources), `Processes` (runs a command and keeps its output), `Postgres` and `Sql`.

`InWorkspace` binds them to the folder of a test (`writeSource`, `javac`, `java`, `mvn`, `generated`, …). JUnit creates the folder with `@TempDir(factory = Workspaces.class)`: an instance field gives a workspace per test method; a static field with `@TestInstance(PER_CLASS)` gives one per class, built once in `@BeforeAll`.

Workspaces are cleared before a test and kept after it, with the sources, the generated files and the output of every command:

```
target/it-test-workspaces/<class>/[<method>/]   ITCase workspaces
target/it-test-workspaces/_dependencies/        the Jakarta EE API and Parsson for javac
target/e2e-test-workspaces/<runtime>/           the e2e application: a Maven project, the logs of the build, of docker and of each node
```

The ITCase and E2E classes use the doer jar of the current build, `0.0.0-IT-SNAPSHOT`, which `mvn verify` installs in `pre-integration-test`. Before running one of them from the IDE, run `mvn -DskipTests verify`.

## The e2e suite

`E2eEnvironment`, a JUnit extension with one instance per JVM, sets up the environment on first use:

1. Postgres and WireMock in a Docker network (Testcontainers);
2. the `E2eApp` of the runtime writes a complete Maven project into `target/e2e-test-workspaces/<runtime>`: the sources of Transit Sims, the DB migrations, and what the runtime needs;
3. `mvn package`; the committed migrations `V1`, `V2` must equal the SQL the processor generated, otherwise the test names the file to copy;
4. node 1 is `docker run --rm` of the built artifact in the image of the runtime (with `--cpus 4`, as on a CI runner), started by `ProcessBuilder`; the test waits for `GET /api/validation/info`. The application migrates the database with Flyway and starts Doer.

The tests use REST (RestAssured), JDBC to Postgres and the WireMock client; `stopNode` (SIGTERM, the exit code must be 143), `startNode` (also a second node on the same database), `appLog` and `threadDump`.

```
mvn verify -Ddoer.e2e.runtime=quarkus                 # build, run all *E2E classes
mvn verify -Ddoer.e2e.runtime=quarkus -Ddoer.e2e.skip-build=true -Dit.test=SmokeE2E
mvn verify -Ddoer.e2e.runtime=external -Ddoer.e2e.base-url=… -Ddoer.e2e.jdbc-url=… -Ddoer.e2e.wiremock-url=…
```

`external` tests an application that is already running, for example the work folder opened in the IDE under a debugger. Without `doer.e2e.runtime` no `*E2E` class runs; from the IDE the default is `quarkus`.

### Runtimes

Each runtime is one class in [`com.doer.e2e`](java/com/doer/e2e). Transit Sims stays the same; what a runtime needs is written into the work folder only, as text blocks with a comment on why. These are the settings a Doer user needs in that runtime.

| Runtime | Class | Artifact and image | What the test adds |
|---|---|---|---|
| Quarkus 3 | `QuarkusApp` | `quarkus-app` in a JRE 25 image | `application.properties`: data source, Flyway at start |
| Spring Boot 4 | `SpringBootApp` | executable jar in a JRE 25 image | `SpringBootMain.java`: CDI scopes as Spring scopes, a transaction-aware `DataSource`, the `Executor`, Jersey resources bound to Spring beans, Doer started and stopped by a `SmartLifecycle`, a `@Bean` for the CDI producer, CDI interceptors as a Spring advisor |
| WildFly 41 | `WildflyApp` | `ROOT.war` in the WildFly image | `transitsims-ds.xml` with system properties (WildFly does not read environment variables there); JSON-B instead of Jackson; `core-threads=200` of the `ManagedExecutorService` (by default as many as processors); a start command with `exec` (`standalone.sh` turns the exit code 143 into 0) |
| Open Liberty 26 | `OpenLibertyApp` | `ROOT.war`, `server.xml` and the driver in the Open Liberty image | `server.xml`: features, data source, context root `/`, INFO on the console, `coreThreads=200`; `flyway.location` (how Flyway finds a location in Liberty) |
| Jetty 12 | `JettyApp` | `ROOT.war` with Weld, Jersey, Narayana and Agroal in the Jetty image | `beans.xml` with the mode `all` (Jersey makes resources without a scope CDI beans only if CDI discovers them), `web.xml`, a transactional `DataSource` of Agroal and Narayana, the `Executor` |

WildFly, Open Liberty and Jetty share `JakartaEeServerApp`: the WAR, `FlywayMigration.java` (an observer of `Startup` called before the one that starts Doer) and `Producers.java`. In the servers it produces the `DataSource` and the `ManagedExecutorService` from JNDI, and `BeanKindSingleton`, because `@jakarta.inject.Singleton` alone is not a bean defining annotation.

### Known flaky tests

`ConcurrencyE2E.queues__should_grow_and_shrink` (WildFly) and `concurrency_10_should_run_10_methods_in_parallel` (Open Liberty) depend on timing and sometimes fail with `--cpus 4`. They stay as they are until Doer's scheduling is improved.
